## 为什么

上游的新协作工具、设置搜索和报告功能有用，本地已有多会话、项目卡和节点验收，需要把整条执行路径适配到这些既有契约。2026-11-26 复核发现上一轮只接五个工具，正式派工、恢复、静默缓冲与暂停继续并未闭合；这不证明功能无法兼容，而是当前实现没有完整交付。用户要求不交付半套功能。

## 已定的行为

- 同一 Bot 保留多个独立会话及并行执行。手动新建、切换和原有会话历史继续可用；不采用上游移除这些能力的 [PR 2039](https://github.com/Fei-Craft/DS-Bot/pull/2039) 和 [PR 2042](https://github.com/Fei-Craft/DS-Bot/pull/2042)。记录状态为“跳过”，理由为用户废弃该删除方案。
- 五个工具必须接入同一完整委托生命周期，原 `message_bot` 与正式 `card_round` 派发也要有清楚的身份衔接；不能只转发旧工具却使追问、答复和取消无法使用。保留既有调用、原卡和原轮，不因工具改名迁移或重建项目任务。
- 项目卡/节点/轮次和 SQLite 仍是正式工作状态。工具工作回传不等于提交或验收通过；`project_task` 的提交、复核和批准规则不变，原卡片和往来 UI 保留。
- 在现有设置导航加入概览、设置搜索和外观实时预览。搜索包含本地“提示词/任务人话解释”等入口；不展示尚未实现或长期排除的功能。
- [PR 2006](https://github.com/Fei-Craft/DS-Bot/pull/2006) 的完整导航重排和操作导览尚未批准，先保留当前导航。它解决设置项多、入口分散的问题，不是新功能的必需前置。
- 缺陷报告的目标为二开仓库 `cooker-code/DS-Bot`。先展示完整脱敏正文和明确目标，用户确认后才允许发布；失败结果不明不自动重发。未配置可用 GitHub 连接器时提供该仓库的草稿提交入口。
- 图片能力单独说明：上游当前报告工具仅接收文本，技能提示用户在 GitHub 手动附加脱敏截图。本次不以文本接口宣称具备自动截图上传；图片上传扩展需有独立、可验证的支持路径。

## 协作的完整流程与验收边界

以下是已确认的功能边界和待完整适配的目标，不能解读为当前.27已经实现。

1. 项目卡派发一轮时登记唯一work，关联原taskId（卡UUID）、round、dispatchId和两端会话。后台执行另有botTaskId，不覆盖本地taskId。
2. 接收者忙碌且请求需要立即执行时，使用独立后台会话；用户可见前台和手动并行会话保留，排队请求仍排队。
3. 追问进入need_input，问题回原派发方；答复回原work/后台会话。其间原卡不提交、不验收，也不产生新轮次。
4. 无实质进展的往返进入paused，原界面能继续或取消；普通问答和有效工作不能误停。静默便条、取消和停止原因忙时缓冲，空闲再注入，CLI/IM/换段保持语义。
5. 完成结果回原卡/轮及正确IM来源，仅提供交付证据，由原项目提交/复核/人工验收规则决定卡状态。
6. 取消只停止指定work及其子工作对应的运行/排队执行；其他卡、其他会话不变，晚到结果不重开或提交。
7. 重启恢复保留原身份和状态：need_input继续等答案，paused继续暂停，已取消/完成不重发，运行中接续原执行；界面回执与存储一致。

完整候选须覆盖正式派工追问/答复/取消、忙时后台、并行会话与换段、等待/暂停/取消后的重启、双卡并发与IM来源、重复恢复只执行一次，以及必要界面继续/取消操作。实现可在专用分支分步进行，核心路径未通过时不得继续合入交付分支或更新日用插件。

## 不做什么

- 不将后台 run 或群空闲直接作为项目卡通过验收。
- 不删除本地多会话，不重做现有项目卡和任务往来布局。
- 不合入本地 dev，不推送或对外发布。新批次在项目主目录 `.worktree/` 下新建专用分支；dev-upsteam 是既有历史候选，本轮审查分支为 docs/upstream-2130-complete-flow。
- 不发送真实测试 Issue，不修改日用源数据库，不重启 DSH。

## 2026-11-26：完整协作流程的本地适配

本轮在 `chore/upstream-2130-complete` 单独实施；`dev@7b9a4fa8` 保持只读。先前 .27 的历史部分采用事实保留，发布版本为 `0.3.10-local.28-upstream`，固定应用候选 `eb05224a` 已完成独立验收，随后安装web与desktop；没有重启日用DSH，加载状态未核实。

| 环节 | 本地行为与完整性条件 |
| --- | --- |
| 正式派工 | `delegate_work(card_round)` 复用原项目派工校验、请求去重和附件，再登记同一 dispatchId 的 work；项目 UUID、派工轮、收件会话分别保存。 |
| 并行执行 | 忙碌时 now 用已有 openParts 机制开独立会话，queue 仍入原会话队列。原前台、手工新建/切换保留；群工作目录、模型与权限跟随该独立执行。 |
| 追问与答复 | work 进入 need_input，答复回原执行。保存 pendingAnswer，避免答复很快到达、旧追问回合尚未结束时误结案。短 W 编号与旧 UUID 都可定位。 |
| 委托树回传 | 子工作回到父工作后，正式 owner 仍可按原 dispatchId 提交；子 Bot 无权提交父轮。协作关闭只生成结果凭据，不代替 project_task submit/approve。 |
| 检查点 | 连续追问暂停；同一配对四次无外部工具自动交接形成返工检查点，ACK 立即受保护。这是自动链需用户确认，不是断言文本没有价值；两步纯文本、正常 fanout 和真实工具工作仍可继续。群内按有向边成环、两次客套/状态帖或四次无工具接力暂停；元工具不能绕过。 |
| 用户控制 | 输入框上方与原 Bot 间对话弹层均显示暂停/待答复，支持 Continue、Answer、Cancel；群 Continue 释放原 parked calls，不另造项目需求。 |
| 静默与取消 | 便笺、取消、停止通知等到空闲才 inject，保留 silent 标记，不开回合、不生成消息泡或未读提示。取消关闭精确子树，清理 worker/caller 队列，抑制迟到回传，原卡只允许通过原恢复或新派工继续。 |
| 重启与存储 | 沿用 split SQLite extra_json 保存 works、workOutbox、protocolSends、silentNotes、pairLoops；完成凭据与完整结果同批保存，稳定 result-workId 去重。inflight 保留协议、父轮、原 part、追问/答复和回传身份；等待与暂停不自动执行，已完成/取消不重复派工。 |
| 换段与 IM | 换段后更新活动派工的执行会话、保留原 work 身份；IM 返回原请求 chat，并重新核对当前配对/绑定。聊天地址保存在私有 work 数据，不写公开 source 或状态列表。 |
