# DS Bot 项目群的任务看板

管理员确认受理时，使用 `project_task reply` 的 `acceptWork: true` 和 `classificationReason` 先保存正式卡，再公布答复。直接交给任务助理、首次要求澄清或提交计划也会按同一收件建卡，重试继续使用原卡。

2026-11-19 · 需求指导，依据 11 月 18 日 `dsh-kanban` 项目会话和本次方向修订。

本篇记录任务看板的产品需求。一期团队状态与二期项目任务的设计分别见[计划一 · 团队状态的 SQLite 存储与无损切换](plans/2026-11-19-team-sqlite-storage.md)和[计划二 · 从一期项目任务到任务详情、分配与终验](plans/2026-11-19-project-task-dispatch.md)。

**人把需求发到群里，默认由管理员 Bot 认可最终产物并结单。群管理员 Bot 负责把需求变成可验收的任务，并一直跟到结单。** 看板给 Bot 派工、接单、交接和查证，也让人随时看到工作到了谁手里、卡在哪里。整条流程由 `ds-bot` 插件提供，只安装它就应能走通。

## 一张需求卡怎样走到验收

| 环节 | 谁做什么 | 原卡上能核实什么 |
| --- | --- | --- |
| 收需求 | 用户在项目群发原话、圈选图或附件。DS Bot 记录收件编号，保留原消息和附件，静默转交管理员。群管理员（例如小圈）判断是独立需求还是已有卡的补充。 | 受理编号能追到原文、可打开的原图和后续卡号。重复投递同一条消息只受理一次。 |
| 首次答复 | 小圈在自己在本群的会话读到明确需求后，用 `project_task reply` 把对具体改动的理解和下一项检查发回原群，再继续规划。能直接回答的提问，用 `chat` 同时发布答案和记录分类。依赖历史事实的提问先查相关记录。 | 同一条用户消息的首答只发布一次。群成员可以看到首答，执行人等到正式派工才开始工作。 |
| 受理和规划 | 管理员确认是新需求时即保存主卡及任务有向无环图（DAG）。每个节点写明谁做、怎么做、交付什么、如何核对，边表示消费哪项前置产物。补充需求归到原卡。 | 第一次派工前就能展开整张图。每张工程卡确定一个工作分支和工作树，各步骤在这棵树上按负责的文件分工。条件待确认时标在对应节点。 |
| 派工和开工 | 管理员从图中挑前置产物齐备的节点，把原需求、附件、上游版本和验收条件送到负责 Bot 的会话。工程 Bot 核对实际分支、提交、目录及环境，匹配后确认开工。 | 同一张卡可看见多个独立节点同时由谁执行。派工已发、对方已收、确认开工分别有据可查。版本不符时展示差异和等待对象。 |
| 交付和交接 | 执行 Bot 带卡号交回产物、实际检查结果、复验方法和遗留问题。管理员按计划把这份交付送给下一位。需要技术复核或集成时由相应 Bot 接手。 | 原始需求独立保留。每轮报告和检查结果归入该轮；开发交回后即能看出下一步等谁、等什么。 |
| 节点中断与接管 | 执行者登记进度，宿主收到中断时按派工轮次记录原因。管理员查看已认可产物、原执行和候选工作树，决定等待、原人续跑、换人或更新计划。 | 详情显示阻塞节点和原因。接手 Bot 在同一节点的新轮收到原图和剩余检查。独立复核继续，迟到回执留在原轮。 |
| 最终验收 | 最后一个未认可节点通过后自动结单。明确要求人工终验时，管理员把最终产物和复验方法交给人。对昨天讨论的工程开发流程，先按仓库授权合入 `main`，核对主线提交与实际预览或构建一致，再送验。其他任务提交约定的产物。 | 卡上留验收入口、对应版本和人的决定。人通过即结单；退回则在原卡记录未通过的场景，管理员安排返工，修正结果重新走到终验。 |

管理员按任务需要选用开发、界面设计、复核、集成等角色。群管理员是这个项目群的派工人，团队级 Main Bot 是 DS Bot 的权限角色，两者可以由同一个 Bot 担任。执行沿用成员已有的模型、权限和会话。

## 人打开看板要看见什么

**列表按任务名找卡，右端箭头打开本任务详情。** 首行显示当前执行 Bot 头像、任务名和状态，任务名称下方依次显示分支、开始时间和执行时长。负责人确认开工后开始计时，交付后固定该轮时长。任务完成后隐藏头像，保留最终计划最早开工到最后提交的时长。详情说明等谁处理、最近交回了什么，并保留各轮记录。

| 卡片详情 | 应当展示的内容 |
| --- | --- |
| 需求与计划 | 默认能读到用户原文、圈选原图和验收条件。管理员的派工计划给出每一步的交付物、检查项和接手人，调整计划时保留调整原因。 |
| 执行与交接 | 按时间展示本卡每个 Bot 的执行回合，可打开对应会话记录。每次交接标明卡号、轮次、发件人、收件人、实际发送的正文和附件。接收后关联到同一条交接；尚未确认接收时就显示“待确认”。 |
| 报错与重试 | 指明哪个 Bot 在哪一步报错、当时能确认的错误、已尝试几次、每次为何再试及结果、现在由谁处理。原因未查明时，保留已观察到的错误。连续出现同一错误且继续尝试缺少依据时，记为阻塞并交管理员决定下一步。 |
| 返工与终验 | 技术复核或人工验收退回时，展示失败场景、预期、证据和接回的 Bot。返工沿原卡开新轮次，原轮次仍可查。读取详情失败时的“重新加载详情”只刷新显示，执行次数保持原值。 |

例如，复核 Bot 发现分页末页仍可点“下一页”，把复现步骤和截图退给开发 Bot。开发 Bot 此时正在处理卡 B，卡 A 显示开发 Bot 头像和本轮实际派工状态。点开 A 的详情能看到退回原因、上轮交付和本轮是否已送达；等开发确认开工，A 才恢复为执行中。

## 公告、任务、目标何时加载

三者都属于群。DS Bot 宿主首次加载团队状态时通过 `state/catalog.sqlite` 定位各群的 `room.sqlite` 并恢复群数据，首次升级时从旧 `state.json` 或已有的 `team.sqlite` 导入并对账；打开群详情时，界面从团队状态视图显示公告、任务列表和目标摘要。**读进宿主内存、显示在界面、送进模型上下文是三个不同的时刻。** [团队状态读取](../ds-bot/src/host/store.js) · [状态视图](../ds-bot/src/host/channel.js) · [群详情](../ds-bot/src/client/details-drawer.js)

| 对象 | 解决的问题 | Bot 什么时候读到 |
| --- | --- | --- |
| 公告 `room.notice` | 全群在发言或协作时都应遵守什么约定。公告仅提供背景。 | 组装成员的群发言提示时附上当时的公告，包括首次群介绍。路由读取独立的任务管理开关。管理员在本群会话收到转交时，收到的是单独构造的收件消息。[群发言提示](../ds-bot/src/host/groups.js) · [路由开关](../ds-bot/src/host/task-routing.js) |
| 任务面板 | 具体这件事由谁负责、是否已开工、交回了什么。群里能并行有多项工作。 | 现有成员工作用 `group_task` 显式登记或查询，工具返回本群工作摘要。项目卡由管理员在受理时调用 `project_task` 查询、建卡或续卡；正式派工时只有本卡的原文、附件、交接要求和验收条件随消息进入负责人会话。打开面板只读取状态。[成员工作](../ds-bot/src/host/tasks.js) · [项目卡工具](../ds-bot/src/host/project-tasks.js) |
| 群目标 `room.goal` | 全群共同要达成什么结果、当前在哪个阶段、用什么证据才能过关。一个群同时有一个当前目标。 | 在普通成员发言轮次准备提示时加载。拟定中提示澄清目标；进行中和暂停时，管理员看到阶段全貌和相应职责，成员看到当前阶段及自己的分工。群初次介绍跳过目标块；目标已完成、已停止或尚未设置时也没有目标块。需要时可调用 `group_goal` 查询。[目标上下文](../ds-bot/src/host/goals.js) · [群目标设计](plans/2026-11-01-group-goal.md) |

例如，“工程任务合入主线后才送人验收”适合写进公告；“让用户能正确翻到最后一页”适合建一张任务卡；若群里确实在分阶段交付整个知识库，再设群目标并把分页列进相应阶段。一张分页卡可以独立派工，无须先创建群目标。

## 单插件派工与当前存储

项目以启用任务管理的群 ID 为边界。宿主根据 `room.admin` 找到当前管理员在本群的会话；管理员从本群成员 ID 中选择负责人。收件、建卡、读卡、派工、开工和交付均由 `ds-bot` 提供。普通项目成员可读本群的卡，建卡和交接须由管理员在自己在本群的会话操作。接单和交付校验接手 Bot、卡号、轮次及实际派工消息。

| 唯一写入位置 | 标识与内容 | 读取时机 |
| --- | --- | --- |
| 群消息账本 | 在群内以消息序号定位原文和附件引用；待归卡的用户消息带 `intakeId`。 | 管理员受理时读取原始消息。正式派工按卡上关联的收件编号取原文和真实附件，图片以图片消息送达负责人。 |
| 本群 `room.sqlite` 中的 `tasks`（来源 `project`）、`task_intakes` 和 `task_rounds` | 正式卡号是 UUID。卡头保留标题、验收条件、关联的收件编号；同群内一个收件编号只归一张卡，多条补充可归同一卡。每轮保留负责人、交接计划、派工消息 ID、指派／送达／开工／交付时间及本轮结果。 | 面板只取卡片摘要。点名读卡的 Bot 可以取回需求和轮次。一期已在途的卡沿用逐轮交接，前轮结果保留。旧版成员工作继续用 `room.tasks[t_…]`，两类记录同屏显示。 |
| 本群收件与计划表 | `project_inbox` 记录收件处理结果。`task_plans`、`task_plan_nodes` 和 `task_plan_dependencies` 保存管理员的整版计划。`task_round_plans` 和 `task_round_inputs` 将实际派工、认可的产物与消费轮次关联。 | 新需求先显示「待受理」。管理员保存计划后即可打开详情。直接前置产物经管理员认可后，各后继节点可分别派工。 |
| DS Bot 请求回执与 Bot 间消息账本 | 本卡本轮正式派工使用固定的请求身份，同次操作重放返回原回执，内容冲突给出错误。轮次中保存的派工消息 ID 关联到实际传递给负责人的消息。 | 接收人显式开工后状态才变为进行中；单纯送达显示等待开工。若投递结果不明，先检查接收记录，再决定是否处理。 |

当前规模下复用群状态的持久化和单写入者规则，可让建卡与收件归属一次保存、群删除时随群移除。图片本体由附件服务管理，卡片只引用原始收件，避开在团队状态里反复复制图片或整段聊天。群名和 Bot 名都可以改，持久记录使用 ID。当前实现以一个项目群为归属单位。[项目卡实现](../ds-bot/src/host/project-tasks.js) · [原文转交](../ds-bot/src/host/project-intake.js) · [群消息账本](plans/2026-11-10-message-ledger.md) · [请求去重](../ds-bot/src/host/requests.js)

当前卡片用指派、送达、开工和提交的实际时间区分状态。计划一先把现有事实完整映射到 SQLite 的群、任务和轮次。计划二再将规划节点及依赖接到同一任务上，状态按实际回执更新。[一期存储模型](design/project-task-model.sql) · [二期规划模型](design/project-task-dispatch.sql)

**当前实现范围**覆盖待受理收件、完整计划、按节点派工和产物复核。代码交付须提供完整提交号，经插件核对本地 `main` 或 `master` 包含该提交后进入待审。报告、只读测试等按交付产物送审。管理员认可产物后，复核与测试等独立后继可以同时开工。一条收件拆成多张独立执行卡、完整的失败与重试时间线仍属前文的产品需求。群任务栏支持按需人工终验和退回。

本次在隔离的 DSH Web 中用模拟模型实际发送过一条带图需求。管理员查成员、建卡、读卡并派给开发 Bot，后者收到原图、确认开工并交回结果。重启宿主后，群详情的任务面板仍显示同一卡号、负责人、轮次和待审状态。自动化用例另外覆盖同一轮重复派工、拒绝错人或错轮次、保留结果交给下一位 Bot。[派工冒烟场景](../ds-bot/dev/smoke.mjs) · [群协作测试](../ds-bot/test/group-work.test.js)

## 首次端到端验收

在只加载 DS Bot 插件的测试项目群中，按下列场景核对。这些是新方案的通过条件。

1. **只发一次需求。** 人发带圈选图的消息后即可离开。管理员建卡派工，开发收到同一卡号和能打开的图。重复投递这条需求、恢复一次中断的派工，最终只有一张卡、一次有效派工。
2. **两张卡同时推进。** A 正在复核，用户发新需求 B，再引用 A 补图。补图只进入 A，B 有自己的记录；看 A 的人能查到这一轮实际发给了谁、对方收到什么。
3. **让同一步骤连续失败。** 卡面能区分执行失败、等待重试和已阻塞。详情解释每次尝试的原因和结果、当前负责人及下一步。重新加载详情、重复收到回执均不增加执行次数。
4. **走完一次退回和终验。** 开发交回后按计划送复核。复核退回而开发正忙时，原卡显示返工原因和排队状态。最后一项获认可即结单。明确要求人工终验的工程任务按约定合入目标主线、核对预览后交人验收；用户可退回原卡，或通过并结单。
