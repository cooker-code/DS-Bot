# DS Bot 程序化设置

每次修改先确定是否影响一个设置的输入、结果、权限、存储或实际生效方式。操作已有团队时，先用目标宿主的 `state` 识别团队、Bot、群和可写状态。使用者从业务动作查下表。开发者从同一条记录追到 `channel.js` 的分派、实际服务和落库位置。

| 要做的事 | 读哪份契约 |
| --- | --- |
| 接入已登录的宿主，查名册，批量改简介、导入或启用技能 | [认证、命令与可执行示例](references/operator.md) |
| 配置 Bot、群成员、目录、分组、模型、全局偏好、共享能力和定时任务 | [团队设置接口](references/team-api.md) |
| 配置连接器、邮件、即时通信、密钥、浏览器、电脑权限及记忆 | [集成与权限接口](references/integration-api.md) |
| 查看 task 或处理执行轮次、会话、批准、诊断与版本更新 | [项目工作与运行接口](references/runtime-api.md) |
| 找对库、核对锁、按 ID 查询或维护停机副本 | [SQLite 操作与一致性](references/storage.md) |

## 怎样决定下一步

1. 用已认证的业务 API 修改设置。它会运行校验、更新宿主内存并触发模型、提示词、会话或能力的生效动作。使用目标项目自己的授权。`401` 表示会话缺失或不匹配，`403` 要检查目标地址与授权，`bot/read-only` 表示该宿主没有写权。接口名或对象不存在要分别核实。
2. 确认当前版本缺少一项业务操作时，先找谁拥有它。属于插件的设置，在对应 `src/host/` 服务实现或复用校验、持久化和生效逻辑，再接入 `channel.js`。DSH 自身的设置接其公开服务。需要宿主新增能力时记录具体缺口、输入和可验证结果。SQLite 只读核查与离线修复见上表。
3. 在同一变更中维护对应接口行。写明业务目的、请求字段的类型与含义、成功值和失败条件、服务函数、数据位置、运行时副作用、回读方法。接口改名或移除时同步更新现有调用方与例子。新增设置页时更新本技能索引。按变更选隔离测试，涉及数据层再核对对应行和重启回读。

从仓库根目录运行 `python3 .agents/skills/ds-bot-doc/scripts/check_contract.py`。DSH 导入文件夹后可用该副本的脚本加 `--repo <DS-Bot 仓库根目录>` 对照指定检出目录。参考文档中的源码相对路径对应仓库内的技能位置。该检查比对当前插件分派器和三份接口表的操作名，也覆盖 `computer-` 分派。参数、语义或存储位置变化仍需审查相关服务与测试。
