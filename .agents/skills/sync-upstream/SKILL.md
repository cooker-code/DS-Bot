# 更新上游插件

从仓库根目录读取 [项目规则](../../../AGENTS.md) 和 [同步记录](../../../scripts/upstream-sync/upstream-changelog.md)。盘点、补记和实施分别按本次委托执行。补记按指定的历史区间取证；只有同步新进展时才刷新 upstream 引用。

## 同步材料的唯一目录

所有上游同步管理内容统一归入仓库的`scripts/upstream-sync/`，以后新增文件也遵守：命令和预检脚本、网页源码、SQLite及备份、upstream-changelog.md、PR评估、功能/设计说明、同步任务材料、验证报告和证据。不再在根目录、`docs/`或技能的`scripts/`/`references/`新建另一套同步材料。

- **受Git管理的代码和文档**：位于本批专用工作树的`scripts/upstream-sync/`。导出只写这个工作树内的`upstream-changelog.md`，禁止为更新入口写入主目录dev。
- **跨工作树共享的运行数据**：固定在主工作目录的`scripts/upstream-sync/upstream.sqlite3`与`backups/`，按精确规则忽略；不随新工作树复制新库。备份用`python3 scripts/upstream-sync/upstream-catalog.py backup`，自动在该目录生成带Asia/Taipei时间的文件。
- `.agents/skills/sync-upstream/SKILL.md`仅保留技能发现入口和约束，其支持脚本/参考资料从上述目录读取。项目通用AGENTS、发布日志仍在既有位置，实际采用的插件源码和上游原始产品设计也沿用模块路径；本条不搬动产品代码。
- 历史回执中的当时分支、绝对工作树、命令和数据路径是历史事实；当前入口、相对链接及新记录使用新目录。迁移目录不刷新PR时间、状态、选择或完整盘点终点。

## 来源与本地集成目标

- 默认来源为 `https://github.com/Fei-Craft/DS-Bot.git` 的 `dev` 分支，本地 remote 名称为 `upstream`。上游已从 **Fei2411/DS-Bot → Fei-Craft/DS-Bot** 迁名，GitHub 仓库 ID 为 `1409013846`。迁名前后沿用同一来源键和已有 PR 条目。
- 每次先核对 `upstream` 实际地址。已确认同一仓库迁名时将该 remote 更新为新地址，并在记录和答复中写明“原仓库 → 新仓库 → 下次同步地址”。来源变更后核对历史祖先关系。
- **每个新的上游同步批次必须新建专用分支和独立工作树，禁止使用本地 `dev`、`main`、`master` 执行移植、合并、提交、构建产物或同步记录写入。** `upstream/dev` 是上游来源，本地 `dev` 只作为只读比较基线，两者不能混淆。分支可命名为 `chore/upstream-<日期>-<批次>`；工作树放在项目主目录 `.worktree/<encodeURIComponent(完整分支名)>/`。
- 新分支默认从固定的本地 `dev` 提交创建；用户指定以 `dev-upsteam` 等候选分支继续适配时，从该指定基线新建本批分支。同一未完成批次的续跑复用已登记的专用分支及工作树；新批次不能沿用已完成批次的分支。
- 验证通过后，结果默认保留在本批专用分支。**执行本技能、通过验收或更新本机 DSH 插件，都不代表授权合回本地 `dev`。** 只有用户当次明确要求将指定候选合回 `dev` 时，才另行执行该集成；远程推送和对外发布同样按当次授权处理。已授权的打包安装可直接使用已验证同步分支，不以先合入 `dev` 为前提。

## 执行前盘点本地改动

在当前实际工作树运行只读脚本，登记本地 `dev` 提交、分支覆盖关系和所有工作树的未提交改动。

```sh
python3 scripts/upstream-sync/preflight.py
```

可用 `--repo <工作树路径>` 指定要检查的检出目录。结果中的 `includedInDev` 是提交祖先关系，`patchesOutsideDev` 补充显示尚未进入 `dev` 的补丁数量；补丁等价和未提交文件仍须按当前内容核对。

1. 比较基线包含本地 `dev` 已集成的开发成果，以及当前工作区里与插件相关的未提交改动。核对其他分支和工作树是否有与待同步模块重叠的改动。分离头工作树也参与盘点。依据实际文件区分源码、文档与依赖缓存。
2. 不为同步上游而自动将其他分支收拢进 `dev`。开发中、未提交或超出本次授权的成果保留在原工作树；已验收且本次获准纳入的成果，只应用到本批专用分支。记录比较范围、未纳入项及行为重叠，关键取舍才询问用户。
3. 首次写入前，在实际执行目录核对 `pwd`、`git branch --show-current`、`git status --short`，确认分支与已登记的本批分支一致，且不是 `dev`、`main`、`master`。若不符，先新建或进入正确工作树再写入，不在原目录暂存改动后补建分支。该检查覆盖代码、技能、版本号及 changelog 等同步材料。
4. 交付时明确写出基线 SHA、本批分支、工作树、已纳入与尚未纳入的本地改动，以及本地 `dev` 是否发生变化。`dev` 有其他会话的新提交时先说明来源差异，不自动把同步结果合回；只有当次明确授权集成时，才核对候选覆盖情况并补验受影响项。

## 按完整业务流程交付，禁止部署半套功能

- 先说明一个功能从入口、身份绑定、执行、等待与答复、完成/取消、重启恢复到界面回执的完整路径，再决定采用范围。同一流程跨多个 PR 时成组适配，不能因为某个补丁或同名工具能运行就交付；不能自行把尚未实现的核心行为改称后续独立功能，借此将半套实现认定为完整采用。
- 已确认不需要的产品/平台可整块排除；这不构成插件功能缺失。插件适用范围仍有断开的核心路径时，整项功能先暂缓，不将已完成片段作为新功能合入或更新日用插件。保留原有逻辑，未完成实现只留在隔离候选分支。
- **禁止把“部分采用”作为当前状态、新条目状态、建议状态或发布结果。** 历史已有片段但整条功能未完成时，当前状态统一为“暂缓”，另列“历史已落地内容、部署版本、验证范围和剩余断点”，注明旧状态→暂缓及时间。完成全部本地适用路径并验证后才能改为“采用”；无法自行决定的产品取舍用“需讨论”，已明确不要用“跳过”。保留历史事实，不静默回退已安装代码或删除在途工作。
- 不能直接合入时，必须列出缺失模块/导出、同名字段的不同含义、真实接口或行为冲突，以及解决方式；补丁上下文不匹配只证明不能直接套用，不能据此断言功能无法共存。后续加固 PR 与前置依赖分开标明。
- 交付以用户能执行完整场景为准。工具注册、单模块测试、代码已包含或旧版验收均不能替代完整流程验证；明确说明当前实现、完整方案和已核实范围。

## 当前条目状态固定为四种

| 状态 | 含义 |
| --- | --- |
| 采用 | 本地适用范围内的改动已完整落地并验证。 |
| 需讨论 | 存在需要用户选择的行为或范围，给出具体场景、选项及建议。 |
| 暂缓 | 功能有价值，但整条本地适用功能尚未完成或验证；说明工程依赖、设计差异和验证缺口，历史部署片段另列。 |
| 跳过 | 属于排除范围、本地已覆盖或已有明确放弃依据。 |

以上是 PR 的采用状态，安装、加载和验证结果另列证据。只盘点时表头写“建议状态”，实施进度统一注明“未实施”，统计也使用“建议采用”等措辞。后续实际落地再更新原条目。

## 未完整采用必须解释原因与解法

每个暂缓项、需讨论项，以及未采用的新功能或设计，都写明以下内容。

- **原因类型与事实**。可多选代码冲突、依赖缺失、设计差异、范围排除、验证缺口、待用户决定等，说明实际文件、接口或数据范围。同文件改动和补丁上下文不匹配时，继续核对具体实现与行为。只有核实了不能同时保留的逻辑，才确认代码冲突。
- **双方差异与影响**。写出上游怎么处理、本地怎么处理，直接套用会影响什么。例如上游按后台任务结案，本地按项目卡节点结案，直接套用可能提前结束原卡。
- **解决方式与通过条件**。工程适配写出修改位置、复用的本地逻辑、前置 PR 和可执行验收场景。需要用户决定时给出选择后各自的实施路径。验证缺口写出缺少的环境或证据以及补证方法。
- **历史落地事实**。历史部署片段放在独立说明字段，不作为第五种状态。写明版本、实际可用路径、验证范围和未完成环节；当前功能仍按完整性判定为暂缓或需讨论。

PR 表使用“原因类型”“实际差异与采用范围”“解决方式与通过条件”列。社区功能表同样提供原因和解决方式。历史批次保留当时事实和时间，本次重审的条目按四状态口径更新，并记明口径调整时间。

## 每个 PR 都要讲清功能作用

逐项解释，不能只列PR号、英文标题、文件清单或“优化/修复”。采用、需讨论、暂缓、跳过都适用。交付表增加“功能作用与例子”，详情保留以下内容：

- **解决什么问题**：谁在什么情况下遇到什么问题；修复项写触发条件及修复前后差别。
- **怎么使用或感知**：给当前项目中的一个具体例子，写入口、操作和预期结果。后台维护/性能项写用户可感知的影响及自动验证方法，不虚构按钮。
- **本地价值和限制**：与本地并行会话、项目卡、UI、存储或权限的关系；依赖、平台排除及未支持情况明确写出。
- **依据**：PR链接、固定合入SHA、相关设计正文；源码与计划分开，不能将后续计划写成已实现。

例如PR2028不能只写“设置概览和搜索”：应解释“团队有多个模型提供方时，概览指出哪些Bot缺Key；用户可到实际配置入口补齐。⌘K搜‘气泡宽度’直接定位对应设置，搜模型可进入批量切换；关闭搜索后未保存草稿仍在”。记录上游实际行为、本地当前可用部分和完整适配缺口，不能因有一个搜索框就判定整项采用。

## 以用户采用判断为目标

用户需要知道upstream新增或改变了什么功能，并判断是否加入自己的代码。先组织“功能变化→用途和场景→上游阶段与限制→本地差异、采用状态和完整解法→原文/PR证据”；不能只把文件或PR堆在网页上。

社区入口与PR设计详情按[社区功能与设计流程](../../../scripts/upstream-sync/references/community-designs.md)维护。上游实现阶段与本地PR四状态分开，设计更新PR与实现PR分开；源内容变化后旧说明标重审。没有plan文件的新功能/修复也要可见。初次补齐历史不冒充本批新增。

## 结构化记录与增量查询

**PR来源、功能评估、验证、用户选择和时间以SQLite台账保存；`scripts/upstream-sync/upstream-changelog.md`是可提交的审计导出。** 数据库固定为主工作目录的`scripts/upstream-sync/upstream.sqlite3`（本机`/Users/blank/wangliang/gitcode/DS-Bot/scripts/upstream-sync/upstream.sqlite3`）。通过`git worktree list --porcelain -z`取得主工作目录，所有专用工作树共用同一库和`backups/`，不得再放到`.git/`、临时目录或其他自选日用路径。它不是DSH团队数据库，不提交SQLite二进制或事务日志。隔离自动测试可显式使用临时库，结束后清理。

SQLite增量台账和HTML管理页已提供，使用[实际命令与页面说明](../../../scripts/upstream-sync/README.md)。在本批专用工作树先查台账，不再从头重复查所有历史PR：

```sh

python3 scripts/upstream-sync/upstream-catalog.py list --q 设置
python3 scripts/upstream-sync/upstream-catalog.py show 2028
# 尚无台账时先bootstrap，默认固定为既有完整盘点终点bb1b1592，不能改成未覆盖的新终点。

python3 scripts/upstream-sync/upstream-catalog.py metadata
python3 scripts/upstream-sync/upstream-catalog.py serve --port 4179
# 同步新进展才明确fetch；补记历史时不fetch。
python3 scripts/upstream-sync/upstream-catalog.py sync --fetch --to upstream/dev
```

结构化事实和用户选择存于主目录的`scripts/upstream-sync/`，同目录内的upstream-changelog.md作为可提交审计。根据pendingAnalysis为每个新PR补齐功能/场景/效果/原因/方案与验证，用annotate登记；再重跑sync完成对账、export更新记录。不得把“已缓存”当作“已评估/采用”。无新变化不建重复批次；来源错误、历史不连续或写失败不推进游标。设计见[台账设计](../../../scripts/upstream-sync/plans/2026-11-26-upstream-catalog.md)。

- 首次从既有来源键导入，后续复用缓存的PR正文、合入SHA、文件列表、设计证据、功能说明和本地判断；先查记录，不重复全历史网络检索。
- 新区间按上次完整盘点终点→本次固定终点补增量，成功对账后才推进游标；失败不跳过。来源历史不连续或本地基线变化时重审受影响项，不能因上游没变就沿用失效的本地结论。
- “我的选择”与实际采用结果分开；用户标记“不需要”的PR，之后增量同步不得覆盖或重新推荐。已采用代码不会因页面标记而自动回滚，取消“不需要”也不自动合入。
- 设计正文、版本和PR关系也存于SQLite，并与普通sync同事务补增量；pendingDesigns补完整中文说明后才推进完整终点。PR唯一键沿用同一来源仓库ID与PR号，直接提交用完整SHA；时间、依赖、原因、方案、验证、版本和历史变更均可追溯。Markdown继续作为可提交的审计交付，不维护两份独立人工事实。

## 每次执行后打开管理网页

- 本技能每次执行结束（包括无新增、只盘点、历史补记和重审），都检查本地管理服务并主动打开`?view=community`页面，不只返回URL。优先用Codex的`open_in_codex`浏览器入口；该入口不可用时用系统浏览器打开实际本地URL。
- 先读服务`/api/meta`核对数据库、执行工作树和分支；已有匹配服务则复用。尚未启动时，从本批专用工作树运行`python3 scripts/upstream-sync/upstream-catalog.py serve --port 4179`并等API可读再打开。端口被其他会话占用时保留它，另选空闲端口并给出实际URL。切换本次自己维护的服务前核对进程归属，不中断其他会话或DSH。
- 来源写入先经SQLite，再导出去重记录；打开前核对导出状态。遇到待补说明或失败，仍可打开已有页面并解释具体缺口，不能把旧页面当成本次同步成功证据。只改技能/管理页不推进上游区间、不重新安装无变化的DSH插件。
- 表格必须显示“PR提交时间”和“同步时间”：前者来自GitHub `pullRequest.createdAt`，后者是该PR来源资料实际入库时间；两者均以Asia/Taipei显示。上游合并时间、首次历史记录日期、分析时间、采用/部署时间分别保留，不相互冒充。GitHub时间只查询缓存缺失项；无来源变化、仅改选择/分析时不刷新同步时间。
- 技能及脚本从其所在的专用工作树解析。主目录仍检出dev时，不假定其旧技能已经包含新流程；交付新版技能的完整路径，未获授权不为更新入口写入dev。

## 盘点与移植

1. **确定区间。** 默认查看 upstream/dev，以记录中该分支最近完整盘点的 SHA 为起点，固定本次终点 SHA。首次用共同祖先。检查祖先关系；不连续时先核对分支历史和已有键。用第一父链枚举区间内的 PR 和直接提交，每项取它相对第一父提交的差异。使用前置盘点固定的本地基线，并记录本次纳入的未提交和未跟踪插件改动。
2. **先看设计说明。** 对整个区间及各项分别做路径差异检查，覆盖 docs/plans/ 正文、目录索引、重命名和删除。阅读改动段落及所在章节。说明新功能解决什么问题、触发条件、行为、限制、旧决定是否改变、哪些只是后续计划，并链接到固定 SHA 的原文。仅补索引和改术语要单独说明。即使暂缓或跳过代码，也在批次中保留对社区功能方向有影响的设计摘要，并在交付答复中直接展示。没有 plan 差异时明确记“本批无设计文档变更”。
3. **判定能否合入。** 给每项评 1–10 分的本地采用优先级。比较上游解决的问题与本地调用路径、任务归属、存储和恢复行为。同一文件的独立改动可分别验证；同一功能有差异时写出双方行为和影响。按项目规则过滤已删除产品及其专用依赖。混合 PR 写清可取与保留部分。补丁套用失败后核对上下文和行为差异，可独立适配并验证的片段继续处理，暂缓项列出实际依赖、冲突或待定行为。
4. **按授权实施。** 只盘点时给出建议状态并标明未实施，需保存的分析记录也写在本批专用分支；实施时只在已核对的本批工作树适配和验证，不把结果应用到 `dev` 工作区。测试按 AGENTS.md 选择，客户端从源码构建。出现可能影响本地核心行为的失败时，用同条件基线判定回归，保留实际未通过项和未定位原因。在同步分支完成所选功能的完整流程适配并验证后，才按已有安装授权从该分支打包并更新本机 DSH profile，核对安装内容并在本批同步记录中写明结果；仅改文档或技能无需重装。不得套用常规发版的“先合 `dev`”规则来自动集成。写明通过、跳过、失败范围及工作区／提交状态。安装、运行实例加载和脚本认证各自报告证据。暂缓项只记录原逻辑、阻塞和重审条件，保留本地实现。
5. **原位更新记录。** PR 的唯一键是来源仓库和 PR 号，直接提交用来源仓库和完整 SHA；同一 PR 跨分支出现仍复用同一行。先查已有键，再新增或更新。每批记录时区、实际记录时间、来源分支和起止 SHA；每项归属首次记录批次。状态或依据变化时在原条目补时间、旧状态→新状态和理由。无变化的重复检查不新增批次、不刷新条目时间。历史片段保持原键，在同一行保留已落地事实和未完成环节。并行编辑时重新读取当前记录再落盘。
6. **更新本地功能说明。** 每批核对固定区间内上游根目录 CHANGELOG.md 的差异，并与本地实际采用的行为逐项对照。实施或补记时，将已采用且用户可感知的功能、行为变化与修复写入根目录 [CHANGELOG.md](../../../CHANGELOG.md) 的本地插件章节，附来源 PR 或批次链接。即使上游尚未写发布说明，也按实际采用结果补齐。历史版本已经落地的行为可保留原发布事实并标明当时范围；暂缓、跳过、仅测试改动和只盘点的候选留在同步记录。已有说明原位更新，保留上游发布章节；本机部署版本与日期继续记在 local-changelog.md。
7. **交付前对账。** 用 Git 区间的键集合对照已登记项（包括以前批次已有的键），检查唯一性、遗漏、plan 文件覆盖，以及本地功能说明与采用结果是否一致；覆盖完整才推进盘点终点。按四种状态分别统计数量，说明是否已实施及关键差异。

后续处理具体缺陷或设计时，以症状、功能名、工具名和模块检索记录中的暂缓、需讨论项及历史落地余项。命中后先向用户指出 PR、上游处理逻辑和本地当时的分歧；结合当前代码判断是否仍适用，按本次授权行动。仅命中关键词不会改变条目状态。

## 交付时直接展示社区方向

每次交付先展示本批**社区新增功能与设计变化**，再展示 PR 采用表。用户应仅凭答复就能理解上游在发展什么能力。逐项说明解决的问题、触发或使用方式、主要限制、上游状态（已合入 dev、已发布或仍在计划）及本地状态，并链接固定 SHA 的设计或来源 PR。本地暂缓、跳过的功能同样参与社区方向说明；没有新功能时说明本批修复和维护的主要方向。同步目录记录保留完整依据。

每批逐项列全 PR，表中保留 1–10 权重和四种显式状态。**交付表格与当前批次的记录表格，按“采用 → 需讨论 → 暂缓 → 跳过”分组，同状态按权重从高到低排列，同权重按 PR 号升序。** 历史落地片段仍保持一个 PR 键，未完成环节写在同一行。旧批次状态或依据变化时原位补时间和理由。

每个采用项及历史已部署片段都给出与本次包版本对应的验证方法。说明操作入口、必要前提、实际步骤、预期结果、已有自动验证和仍缺的真实环境证据。性能、超时或资源回收修复优先复用隔离测试，界面可观察的功能提供用户能执行的验证步骤。按 [安装、加载与行为验证](../../../scripts/upstream-sync/references/verification.md) 组织交付，具体用例随本批实际采用内容更新到同步目录记录。

交付还应说明本批分支及工作树、候选提交、是否合回 `dev`（默认未合回）、版本、安装包、已更新 profile、运行加载状态，以及仍未通过的检查。仓库迁名时明确下一次的来源地址。

## Desktop 认证状态的解释

按 [ds-bot-doc 的认证流程](../ds-bot-doc/references/operator.md) 核对当前 Desktop。`login_http_401` 表示已找到宿主，但脚本使用的登录材料在登录交换时未被接受，可能失效或与本次进程不匹配。这时运行状态读取尚未完成，应说明缺少当前实例可接受的正式会话。

安装结论依据实际 profile 的包版本、客户端及宿主文件核对。运行加载结论依据当前实例的版本或行为。认证失败时保留已取得的安装证据，并将运行加载记为未核实，向用户解释本次受影响的检查。延续从 Dock 启动的习惯，使用既有授权的官方登录材料进行后续查询。
