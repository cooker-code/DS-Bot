# 更新上游插件

从仓库根目录读取 [项目规则](../../../AGENTS.md) 和 [同步记录](../../../upstream-changelog.md)。盘点、补记和实施分别按本次委托执行。补记按指定的历史区间取证；只有同步新进展时才刷新 upstream 引用。

## 来源与本地集成目标

- 默认来源为 `https://github.com/Fei-Craft/DS-Bot.git` 的 `dev` 分支，本地 remote 名称为 `upstream`。上游已从 **Fei2411/DS-Bot → Fei-Craft/DS-Bot** 迁名，GitHub 仓库 ID 为 `1409013846`。迁名前后沿用同一来源键和已有 PR 条目。
- 每次先核对 `upstream` 实际地址。已确认同一仓库迁名时将该 remote 更新为新地址，并在记录和答复中写明“原仓库 → 新仓库 → 下次同步地址”。来源变更后核对历史祖先关系。
- 默认将已验证的选择性移植合入**本地 `dev`**。从固定的本地 `dev` 提交建立隔离任务分支和工作树，按项目规则验收后集成、发本地版本并更新日用安装。远程推送和对外发布按用户当次授权执行。

## 执行前盘点本地改动

在当前实际工作树运行只读脚本，登记本地 `dev` 提交、分支覆盖关系和所有工作树的未提交改动。

```sh
python3 .agents/skills/sync-upstream/scripts/preflight.py
```

可用 `--repo <工作树路径>` 指定要检查的检出目录。结果中的 `includedInDev` 是提交祖先关系，`patchesOutsideDev` 补充显示尚未进入 `dev` 的补丁数量；补丁等价和未提交文件仍须按当前内容核对。

1. 比较基线包含本地 `dev` 已集成的开发成果，以及当前工作区里与插件相关的未提交改动。核对其他分支和工作树是否有与待同步模块重叠的改动。分离头工作树也参与盘点。依据实际文件区分源码、文档与依赖缓存。
2. 其他分支中已验收且获准集成的成果按项目规则收拢，再固定最终 `dev` 基线。开发中、未提交或超出本次授权的成果保留在原工作树，在同步记录中说明比较范围与未纳入项；有关联时核对具体冲突和行为影响，关键取舍才询问用户。
3. 交付时明确写出基线 SHA、执行前是否收拢其他分支、已纳入与尚未纳入的本地改动。当前工作树干净只能证明该检出目录的状态。
4. 集成前再核对本地 `dev` 是否前进。候选覆盖新增的本地提交后，按实际变化补验受影响项，再集成获验收的结果。

## 长期跳过的上游内容

- DS Bot 独立桌面应用（`app/`、`start.ps1`）及其安装包。
- iOS 和 Android 客户端（`mobile/`），以及手机配对、远程访问和加密中继（`link/`）。
- Docker 部署（`docker/`、`docker-compose.yml`、`docker-compose.dev.yml`）。
- Windows 和 Linux 专用代码、测试、夹具与 CI 作业。本地维护 macOS 插件，跨平台 PR 仍评估 macOS 适用部分。

按实际用途判断，包括上述模块新增或改名的文件，以及仅服务于它们的依赖、文档、测试和构建发布任务。遇到上游修改本地已删除的模块，保留删除结果。只涉及排除范围的 PR 仍在同步记录登记为“跳过”，注明所属模块。混合 PR 在同一条目写清取舍，只移植插件需要的部分。DSH Desktop 或 DSH Web 加载插件时的修复仍参与评估，例如标题写“手机布局”的改动也可能修复 DSH Web 的窄屏显示。

因本地设计差异暂缓的功能保留重审线索。单次跳过的贡献流程、文档或持续集成改动只代表当批决定。

## 条目状态固定为五种

| 状态 | 含义 |
| --- | --- |
| 采用 | 本地适用范围内的改动已完整落地并验证。 |
| 部分采用 | 已验证落地一部分，本地适用范围仍有余项未采用。逐项列出已采用和余项。 |
| 需讨论 | 存在需要用户选择的行为或范围，给出具体场景、选项及建议。 |
| 暂缓 | 功能有价值，当前因工程依赖、实现或设计差异、验证缺口等尚未采用。 |
| 跳过 | 属于排除范围、本地已覆盖或已有明确放弃依据。 |

以上是 PR 的采用状态，安装、加载和验证结果另列证据。只盘点时表头写“建议状态”，实施进度统一注明“未实施”，统计也使用“建议采用”等措辞。后续实际落地再更新原条目。

## 暂缓和部分采用必须解释原因与解法

每个暂缓项、部分采用的余项，以及未采用的新功能或设计，都写明以下内容。

- **原因类型与事实**。可多选代码冲突、依赖缺失、设计差异、范围排除、验证缺口、待用户决定等，说明实际文件、接口或数据范围。同文件改动和补丁上下文不匹配时，继续核对具体实现与行为。只有核实了不能同时保留的逻辑，才确认代码冲突。
- **双方差异与影响**。写出上游怎么处理、本地怎么处理，直接套用会影响什么。例如上游按后台任务结案，本地按项目卡节点结案，直接套用可能提前结束原卡。
- **解决方式与通过条件**。工程适配写出修改位置、复用的本地逻辑、前置 PR 和可执行验收场景。需要用户决定时给出选择后各自的实施路径。验证缺口写出缺少的环境或证据以及补证方法。
- **部分采用的边界**。已采用部分列验证证据，余项分别说明暂缓或跳过理由，以及后续适配或结束跟踪的条件。

PR 表使用“原因类型”“实际差异与采用范围”“解决方式与通过条件”列。社区功能表同样提供原因和解决方式。历史批次保留当时事实和时间，本次重审的条目按五状态口径更新，并记明口径调整时间。

## 盘点与移植

1. **确定区间。** 默认查看 upstream/dev，以记录中该分支最近完整盘点的 SHA 为起点，固定本次终点 SHA。首次用共同祖先。检查祖先关系；不连续时先核对分支历史和已有键。用第一父链枚举区间内的 PR 和直接提交，每项取它相对第一父提交的差异。使用前置盘点固定的本地基线，并记录本次纳入的未提交和未跟踪插件改动。
2. **先看设计说明。** 对整个区间及各项分别做路径差异检查，覆盖 docs/plans/ 正文、目录索引、重命名和删除。阅读改动段落及所在章节。说明新功能解决什么问题、触发条件、行为、限制、旧决定是否改变、哪些只是后续计划，并链接到固定 SHA 的原文。仅补索引和改术语要单独说明。即使暂缓或跳过代码，也在批次中保留对社区功能方向有影响的设计摘要，并在交付答复中直接展示。没有 plan 差异时明确记“本批无设计文档变更”。
3. **判定能否合入。** 给每项评 1–10 分的本地采用优先级。比较上游解决的问题与本地调用路径、任务归属、存储和恢复行为。同一文件的独立改动可分别验证；同一功能有差异时写出双方行为和影响。按项目规则过滤已删除产品及其专用依赖。混合 PR 写清可取与保留部分。补丁套用失败后核对上下文和行为差异，可独立适配并验证的片段继续处理，暂缓项列出实际依赖、冲突或待定行为。
4. **按授权实施。** 只盘点时给出建议状态并标明未实施；实施时在含本地实际改动的隔离副本中验证候选，再应用到目标工作区。测试按 AGENTS.md 选择，客户端从源码构建。出现可能影响本地核心行为的失败时，用同条件基线判定回归，保留实际未通过项和未定位原因。合入插件代码并验证后，按 AGENTS.md 的“更新本机 DSH 插件”同步日用 profile，核对安装内容并在本批同步记录中写明结果。写明通过、跳过、失败范围及工作区／提交状态。安装、运行实例加载和脚本认证各自报告证据。暂缓项只记录原逻辑、阻塞和重审条件，保留本地实现。
5. **原位更新记录。** PR 的唯一键是来源仓库和 PR 号，直接提交用来源仓库和完整 SHA；同一 PR 跨分支出现仍复用同一行。先查已有键，再新增或更新。每批记录时区、实际记录时间、来源分支和起止 SHA；每项归属首次记录批次。状态或依据变化时在原条目补时间、旧状态→新状态和理由。无变化的重复检查不新增批次、不刷新条目时间。部分采用保持一个键，在同一行写明余项。并行编辑时重新读取当前记录再落盘。
6. **更新本地功能说明。** 每批核对固定区间内上游根目录 CHANGELOG.md 的差异，并与本地实际采用的行为逐项对照。实施或补记时，将已采用且用户可感知的功能、行为变化与修复写入根目录 [CHANGELOG.md](../../../CHANGELOG.md) 的本地插件章节，附来源 PR 或批次链接。即使上游尚未写发布说明，也按实际采用结果补齐。部分采用只写已落地的行为；暂缓、跳过、仅测试改动和只盘点的候选留在同步记录。已有说明原位更新，保留上游发布章节；本机部署版本与日期继续记在 local-changelog.md。
7. **交付前对账。** 用 Git 区间的键集合对照已登记项（包括以前批次已有的键），检查唯一性、遗漏、plan 文件覆盖，以及本地功能说明与采用结果是否一致；覆盖完整才推进盘点终点。按五种状态分别统计数量，说明是否已实施及关键差异。

后续处理具体缺陷或设计时，以症状、功能名、工具名和模块检索记录中的暂缓或部分采用项。命中后先向用户指出 PR、上游处理逻辑和本地当时的分歧；结合当前代码判断是否仍适用，按本次授权行动。仅命中关键词不会改变条目状态。

## 交付时直接展示社区方向

每次交付先展示本批**社区新增功能与设计变化**，再展示 PR 采用表。用户应仅凭答复就能理解上游在发展什么能力。逐项说明解决的问题、触发或使用方式、主要限制、上游状态（已合入 dev、已发布或仍在计划）及本地状态，并链接固定 SHA 的设计或来源 PR。本地暂缓、跳过的功能同样参与社区方向说明；没有新功能时说明本批修复和维护的主要方向。根目录记录保留完整依据。

每批逐项列全 PR，表中保留 1–10 权重和五种显式状态。**交付表格与当前批次的记录表格，按“采用 → 部分采用 → 需讨论 → 暂缓 → 跳过”分组，同状态按权重从高到低排列，同权重按 PR 号升序。** 部分采用仍保持一个 PR 键，余项写在同一行。旧批次状态或依据变化时原位补时间和理由。

每个采用或部分采用项都给出与本次包版本对应的验证方法。说明操作入口、必要前提、实际步骤、预期结果、已有自动验证和仍缺的真实环境证据。性能、超时或资源回收修复优先复用隔离测试，界面可观察的功能提供用户能执行的验证步骤。按 [安装、加载与行为验证](references/verification.md) 组织交付，具体用例随本批实际采用内容更新到根目录同步记录。

交付还应说明集成分支、版本、安装包、已更新 profile、运行加载状态，以及仍未通过的检查。仓库迁名时明确下一次的来源地址。

## Desktop 认证状态的解释

按 [ds-bot-doc 的认证流程](../ds-bot-doc/references/operator.md) 核对当前 Desktop。`login_http_401` 表示已找到宿主，但脚本使用的登录材料在登录交换时未被接受，可能失效或与本次进程不匹配。这时运行状态读取尚未完成，应说明缺少当前实例可接受的正式会话。

安装结论依据实际 profile 的包版本、客户端及宿主文件核对。运行加载结论依据当前实例的版本或行为。认证失败时保留已取得的安装证据，并将运行加载记为未核实，向用户解释本次受影响的检查。延续从 Dock 启动的习惯，使用既有授权的官方登录材料进行后续查询。
