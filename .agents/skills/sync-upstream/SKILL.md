# 更新上游插件

从仓库根目录读取 [项目规则](../../../AGENTS.md) 和 [同步记录](../../../upstream-changelog.md)。盘点、补记和实施分别按本次委托执行。补记按指定的历史区间取证；只有同步新进展时才刷新 upstream 引用。

## 长期跳过的上游内容

- DS Bot 独立桌面应用（`app/`、`start.ps1`）及其安装包。
- iOS 和 Android 客户端（`mobile/`），以及手机配对、远程访问和加密中继（`link/`）。
- Docker 部署（`docker/`、`docker-compose.yml`、`docker-compose.dev.yml`）。

按实际用途判断，包括上述模块新增或改名的文件，以及仅服务于它们的依赖、文档、测试和构建发布任务。遇到上游修改本地已删除的模块，保留删除结果。只涉及排除范围的 PR 仍在同步记录登记为“跳过”，注明所属模块。混合 PR 在同一条目写清取舍，只移植插件需要的部分。DSH Desktop 或 DSH Web 加载插件时的修复仍参与评估，例如标题写“手机布局”的改动也可能修复 DSH Web 的窄屏显示。

因本地设计差异暂缓的功能保留重审线索。单次跳过的贡献流程、文档或持续集成改动只代表当批决定。

## 盘点与移植

1. **确定区间。** 默认查看 upstream/dev，以记录中该分支最近完整盘点的 SHA 为起点，固定本次终点 SHA。首次用共同祖先。检查祖先关系；不连续时先核对分支历史和已有键。用第一父链枚举区间内的 PR 和直接提交，每项取它相对第一父提交的差异。保留本地已提交、未提交和未跟踪的插件改动作为实际比较基线。
2. **先看设计说明。** 对整个区间及各项分别做路径差异检查，覆盖 docs/plans/ 正文、目录索引、重命名和删除。阅读改动段落及所在章节。说明新功能解决什么问题、触发条件、行为、限制、旧决定是否改变、哪些只是后续计划，并链接到固定 SHA 的原文。仅补索引和改术语要单独说明。即使决定暂缓代码，也在批次中保留设计摘要。没有 plan 差异时明确记“本批无设计文档变更”。
3. **判定能否合入。** 给每项评 1–10 分的本地采用优先级。比较上游解决的问题与本地调用路径、任务归属、存储和恢复行为。同一文件的独立改动可分别验证；同一功能有差异时写出双方行为和影响。按项目规则过滤已删除产品及其专用依赖。混合 PR 写清可取与保留部分。
4. **按授权实施。** 只盘点时记“可合入”；实施时在含本地实际改动的隔离副本中验证候选，再应用到目标工作区。测试按 AGENTS.md 选择，客户端从源码构建。合入插件代码并验证后，按 AGENTS.md 的“更新本机 DSH 插件”同步日用 profile，核对安装内容并在本批同步记录中写明结果。写明通过、跳过、失败范围及工作区／提交状态。暂缓项只记录原逻辑、阻塞和重审条件，保留本地实现。
5. **原位更新记录。** PR 的唯一键是来源仓库和 PR 号，直接提交用来源仓库和完整 SHA；同一 PR 跨分支出现仍复用同一行。先查已有键，再新增或更新。每批记录时区、实际记录时间、来源分支和起止 SHA；每项归属首次记录批次。状态或依据变化时在原条目补时间、旧状态→新状态和理由。无变化的重复检查不新增批次、不刷新条目时间。部分采用保持一个键，在同一行写明余项。并行编辑时重新读取当前记录再落盘。
6. **更新本地功能说明。** 每批核对固定区间内上游根目录 CHANGELOG.md 的差异，并与本地实际采用的行为逐项对照。实施或补记时，将已采用且用户可感知的功能、行为变化与修复写入根目录 [CHANGELOG.md](../../../CHANGELOG.md) 的本地插件章节，附来源 PR 或批次链接。即使上游尚未写发布说明，也按实际采用结果补齐。部分采用只写已落地的行为；暂缓、跳过、仅测试改动和只盘点的候选留在同步记录。已有说明原位更新，保留上游发布章节；本机部署版本与日期继续记在 local-changelog.md。
7. **交付前对账。** 用 Git 区间的键集合对照已登记项（包括以前批次已有的键），检查唯一性、遗漏、plan 文件覆盖，以及本地功能说明与采用结果是否一致；覆盖完整才推进盘点终点。报告实际采用、可合入、暂缓和跳过的数量及关键差异。

后续处理具体缺陷或设计时，以症状、功能名、工具名和模块检索记录中的暂缓或部分采用项。命中后先向用户指出 PR、上游处理逻辑和本地当时的分歧；结合当前代码判断是否仍适用，按本次授权行动。仅命中关键词不会改变条目状态。
