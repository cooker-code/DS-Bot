# 新包是否正确接入

每批从专用同步分支的 local-changelog.md 和交付包取得四段版本与 npm 版本，使用本批版本作为预期值。验收表分别记录安装内容、运行加载和功能行为，关联同一个包和已验收提交，并登记分支及工作树。候选通过检查或安装到日用 profile 不代表已合回 `dev`，也不授权执行该合并。

## 安装内容

由执行者核对日用 profile 的实际安装路径。包安装比较包内版本、client.js 以及本次变更的宿主文件，链接安装核对真实指向和构建产物。已有完整逐文件比对证据可复用。回执写明 profile、安装方式、版本、包路径及核对结果。

## 运行加载

用户结束正在进行的会话后，照常退出 DSH 并从 Dock 重新打开。在 **DS Bot 设置 → About DS Bot（关于 DS Bot）** 查看版本，核对本批 npm 版本。

该页面的 `update.current` 来自 [update.js](../../../../ds-bot/src/host/update.js) 模块初始化时保存的包版本，由 [AboutPage](../../../../ds-bot/src/client/about.js) 显示，可用于核对宿主插件初始化版本。诊断报告的 `botVersion` 会读取当前磁盘上的 package.json，使用时应结合初始化版本与本批功能行为。

执行者有有效会话时，可通过现有 `update-check` 业务入口读取 `current`，按 ds-bot-doc 的认证契约调用。HTTP 401 时记录认证缺口，保留用户通过关于页核对的入口。实际查询的 API 名称应先与当前分派器核对。

## 完整流程是新功能的交付前提

先用一个真实业务场景证明入口到最终回执闭合。协作类场景至少覆盖派活绑定原项目卡/轮次、接收方忙时的执行去向、追问与答复、完成回传、取消、暂停继续和重启恢复，以及实际所需的 IM 来源与界面操作。测试应断言这些边界按本地约定衔接，而不是只检查五个工具存在。

没有完整证据时保留旧流程，候选留在专用分支，不把片段安装到日用 profile。历史半套版本标记实际版本和已知断点；诊断用例确认某个错误能够复现，不表示该功能验收通过。代码已被包含、过去版本已结单或局部测试通过，都不能作为新流程通过证据。

## 功能行为

为每个采用项和历史已部署片段给出可复查用例。当前采用状态仅四种；尚未闭合的历史功能标为暂缓，保留片段的版本与验证边界，不再使用“部分采用”状态。

| 内容 | 应记录什么 |
| --- | --- |
| 前提和入口 | 使用哪个测试 Bot、测试群、模型或已连接的平台，哪些环境必须存在。 |
| 步骤 | 从功能正常入口触发改动。涉及外发或配置修改时沿用本次授权与目标范围。 |
| 预期 | 用户可以观察或自动断言的结果。 |
| 已有证据 | 对应本批候选的测试、实际观察、包版本和清理结果。 |
| 尚缺证据 | 明确真实 CLI、平台或运行实例尚未验证的范围。 |

例如 Telegram 格式改动，可在已绑定的测试聊天中让 Bot 输出三级标题及两行表格，观察标题加粗、表格转为逐行条目、内容完整。Gemini 畸形响应重试、连接器断开和录音启动失败等场景用隔离模型或协议夹具触发，保留重试预算、释放资源等断言。Codex 恢复测试核对会话 A 回收后能够重新调用团队工具，同时会话 B 的进程和工作继续。

用户通常只需核对关于页版本，再选自己实际使用的一项功能做真实场景确认。执行者完成其余适用的自动检查，将每项结果留在同一版本的验收表。配置和连接尚不存在的场景记录为未验证，并写出补验前提。

## 已有失败

对候选与基线同条件复现的失败，记录实际失败、基线对照和剩余影响。本批采用的修复按各自证据交付，已有失败继续单列。需要解决既有问题时，按相关上游 PR 和本地实现另行定位。
