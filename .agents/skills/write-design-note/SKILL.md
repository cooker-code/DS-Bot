# 写设计文档

让后来的人能用这份文档回答两个问题：遇到这个场景应该发生什么？当初为什么这样定？

## 先确定写在哪一篇

先查目录索引和相邻主题。同一功能已有设计时，优先修改原文；独立的新主题再另起一篇。分清用户已拍板的选择、实现中观察到的事实和仍在讨论的问题。代码可以佐证现状；代码与设计冲突时，指出具体差异，不凭实现推定设计已经变更。用户要草案时可以先写，标明草案，把会改变行为的未决项单列为「待确认」。

在 DS Bot 中，以 [设计目录说明](../../../docs/plans/README.md) 和 [贡献指南](../../../CONTRIBUTING.zh.md) 为准。修改行为前对照[项目愿景](../../../docs/vision.md)和相关设计；涉及界面时也读[界面规范](../../../docs/design/ui-standard.md)。大功能的设计随代码在同一个拉取请求（PR）里评审。改变已定设计先在 Issue 里与维护者确认；修复偏离既定规则的缺陷通常无需新增设计文档。把本 skill 用到其他仓库时，沿用目标项目的目录、评审和归档约定。

## 新写一篇

本项目用中文，文件名按设计定下的日期和简短英文主题命名，如 `docs/plans/2026-11-10-group-todos.md`。下面是正文骨架，起草时用实际内容替换提示，只引用真实存在的 Issue、PR 或相关设计。

```markdown
# 功能或行为名称

- 日期：设计定下的日期
- 相关：关联的 Issue、PR 或设计文档

## 为什么

谁在什么场景遇到了什么问题；选择这个做法时，哪项取舍决定了结果。

## 已定的行为

- 写清谁在什么条件下做什么，以及用户、调用方或下次读取时能观察到什么结果。

## 不做什么

写这次明确排除、又容易被读者误以为包含的能力。

## 已知限制

写设计按预期工作时，使用者仍会遇到的限制及其影响。

## 变更

- 变更日期：具体改了哪条规则，有对应 PR 时附编号。
```

**从一个能判断对错的场景下笔。** 例如「群聊支持共享待办」还不足以判断第 101 条该怎么办。《群聊共享待办》给出了结果：已有 100 条时拒绝新增，保留原条目，并提示先删除一条或清空已完成项。它也交代了同一条重复勾选的结果。只有权限、上限、重试、持久化等细节确实影响该功能时，才把它们写进规则；数值和接口名取自已确认的设计。[群聊共享待办](../../../docs/plans/2026-11-10-group-todos.md)

**复杂交互按读者会问的问题拆开。** 《读长回复》在「已定的行为」下依次写什么时候出现阅读胶囊、怎样判定当前小节、点目录项后停在哪里。「不做什么」交代折叠规则属于原设计；「已知限制」则交代胶囊会遮住一行开头。小功能用几条规则就能说清时，保留平铺列表即可。[读长回复](../../../docs/plans/2026-11-13-long-reply-reading.md)

## 修订与交付

- 修订时，把受影响的规则直接改成新的约定，保留篇首原始日期和文末历史，再在「变更」追加这次的日期、差异及已有的 PR。只改措辞时保留原有决策。比如共享待办后来支持删除单条和清空已完成，正文同步更新了可用操作和满额提示，文末另记这次变化。
- 在 DS Bot 的设计目录正式新增一篇时，在目录 README 的索引加一行，用一句话说明读者能从它查到什么；修订原文时按需更新已有摘要。
- 交付前只看成稿，选一个典型操作和一个与本设计有关的边界，尝试说出可观察的结果。需要靠猜才能作答时，补上有依据的规则，或把尚未决定之处标明。检查篇首关联和索引链接是否指向正确对象。
