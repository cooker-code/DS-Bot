# 核实所问版本的架构

先确认问题指向集成分支、某个 task 的候选、未提交的工作区，还是已部署版本。进入该工作树，用 `git rev-parse --show-toplevel`、`git branch --show-current`、`git rev-parse HEAD`、`git status --short --untracked-files=all` 识别实际对象。用户询问线上现状时，还要从可访问的部署或运行记录确认实际版本。

- **维护索引。** 架构责任人维护集成分支的共享索引。功能分支需要检索时在它自己的工作树建索引。先运行 `gitnexus status --json` 比对仓库、分支与索引提交。对支持分支索引的版本，维护人可在已确认的具名分支运行 `gitnexus analyze --index-only --branch "$branch"` 并再查状态，其中 `branch` 取自该工作树的 `git branch --show-current`。同一索引只由一方刷新。遇到分离头指针、版本不符、工具缺失或只读工作树，直接查目标提交的源码也能继续。
- **核实影响。** 在工作树根目录用 `gitnexus context "$symbol" --repo "$PWD" --branch "$branch" --file "$file"` 定位具体符号，按项目的真实符号和文件填写变量。读调用双方、触发条件、读写端和下游。未提交的部分检查暂存、未暂存差异及未跟踪文件。动态注册、消息投递或零命中时，接着查入口绑定、配置或针对性测试。索引和源码不一致时记录缺失关系、替代证据及负责刷新的人。
- **交付证据。** 给出工作树、分支、提交、本地差异范围，以及“入口 → 处理 → 存储或下游”的文件与符号。标明仍待核实的运行条件。候选变更时通知依赖该结论的成员复核。项目采用 Diffmap 时把有实际变化的技术栈、目录职责、存储和数据流更新到受影响章节并校验，向助理提供章节与候选版本供完成报告引用。
