# 触发模式

以下用户原话应让 AI 考虑使用 `trellis mem`。请据此校准直觉：若用户消息符合其中一种模式而你没有使用 `mem`，很可能遗漏了一段显而易见的回忆。模式按表述背后的**意图**而非表面用词分组；相同意图会以不同语言和语气出现。

## 回忆过去的解决方案

用户在问“以前我们（或我）怎么解决这个问题”。过去对话保存了答案；代码库只展示结果，未必展示当时的推理。

- “上次怎么解的？”
- “最后我们对 X 怎么处理的？”
- “这个之前不是已经解决过一次吗？”
- “之前是怎么搞定 X 的？”
- “我记得以前修过类似的”
- “How did we solve this last time?”

执行：`trellis mem search "<symptom keyword>" --global --limit 10`，再对最接近的结果运行 `context`。

## 检索旧决定

用户引用一个存在于旧对话、而非任何已提交文件中的决定。应查看 brainstorm 窗口。

- “关于 X 的决定是什么？”
- “我们是否决定使用 Postgres 还是 SQLite？”
- “选择 X 而非 Y 的理由是？”
- “我们当时为啥选了 X 而不是 Y？”
- “关于 X 我们之前是怎么定的？”
- “之前讨论过 X 的方案吗？”

执行：先用 `trellis mem search "<decision keyword>"` 找到会话，再运行 `extract <id> --phase brainstorm` 恢复讨论。

## 跨会话继续

用户间隔一段时间后恢复工作，背景没有明说。

- “我们做到哪了？”
- “继续上次的。”
- “从上次停下的地方继续。”
- “继续上次的”
- “我们上次做到哪了”
- “接着昨天那个任务”

执行：`trellis mem list --task <current-task-dir>` 找到与当前 task 关联的最近会话，再用 `extract` 导出最后一个会话。

## 排查熟悉的缺陷

当前缺陷像以前见过的问题，过去会话很可能记录了解法。

- “我感觉以前碰到过这个。”
- “这不像上个月的那个 bug 吗？”
- “和我在 X 中遇到的 timeout 是同一种吗？”
- “这个错好像之前见过”
- “这个 bug 是不是上次那个？”
- “怎么又是这个 error？”

执行：`trellis mem search "<error message fragment>" --global`。使用真实错误信息中短而有区分度的片段。

## 识别自身重复模式

用户询问自己是否反复犯同一类错误或重复作出相同决定。

- “我是否总是犯这个错误？”
- “我遇到 X 有多频繁？”
- “这对我来说是反复发生的吗？”
- “我每次都踩这个坑吗？”
- “我老犯这个错？”
- “这类问题之前出现过几次？”

执行：`trellis mem search "<topic>" --global --limit 50`，查看列表中的日期和项目；需要时用 `extract` 导出两三段结果进行比较。

## finish-work 复盘（按需）

用户明确要回顾本任务，而非将此作为强制步骤。

- “总结这次任务做了什么。”
- “主要决定和意外是什么？”
- “写下这轮的经验教训。”
- “总结一下这次的经验”
- “记一下这次踩的坑”
- “复盘下这个任务”

执行：从 `.trellis/.runtime/sessions/*.json` 或 `mem list --task <task-dir>` 确定当前任务的 session id，再分别运行 `extract <id> --phase brainstorm` 和 `--phase implement`。给出总结时，尽可能附上具体的 file:line 引用。是否还要把总结写入 PRD、spec 或注记文件由用户决定；可以建议，不能自动写入。

## 不应触发 `mem` 的反例

- “这个函数做什么？”→ 直接读文件。
- “这个测试为何失败？”→ 先读测试输出和文件。
- “我们代码库中 X 的正确模式是什么？”→ grep / 阅读 spec 文件。
- “Y 的最新 npm 版本是什么？”→ 调用 `npm view`。
- “修这个 bug。”→ 先调试；只有确实怀疑存在旧上下文时才检索 `mem`，否则只会制造噪声。

标准不变：资深同事会不会在回答前问“这事我们之前是不是谈过？”会，就使用 `mem`；不会，就不要使用。
