# 代码质量检查

对最近编写的代码进行全面质量验证，结合 Spec 合规、跨层安全和提交前检查。

---

## Step 1：识别变更

```bash
git diff --name-only HEAD
git status
```

## Step 2：读取 Task 产物和适用 Spec

按顺序读取当前 Task 产物：

- `prd.md`
- `design.md`（如存在）
- `implement.md`（如存在）

```bash
python3 ./.trellis/scripts/get_context.py --mode packages
```

对每个已变更的包/层，读取 Spec 索引并遵循其 **质量检查** 部分：

```bash
cat .trellis/spec/<package>/<layer>/index.md
```

读取其中引用的具体规范文件——索引是指针，不是终点。

## Step 3：运行项目检查

运行项目的 lint、type-check 和测试命令。修复所有失败后再继续。

## Step 4：按清单审查

### 代码质量

- [ ] lint 工具是否通过？
- [ ] 类型检查器是否通过（如适用）？
- [ ] 测试是否通过？
- [ ] 是否没有遗留调试日志？
- [ ] 是否没有被抑制的警告或类型安全绕过？

### 测试覆盖

- [ ] 新函数 → 是否添加单元测试？
- [ ] 缺陷修复 → 是否添加回归测试？
- [ ] 行为变更 → 是否更新现有测试？

### Spec 同步

- [ ] `.trellis/spec/` 是否需要更新（新模式、约定、经验）？

> “如果我修复了缺陷或发现非显而易见的内容，是否应该记录下来，避免未来再次遇到？”→ 如果答案为“是”，更新相关 Spec 文档。

### 文档复杂度与正确性

- [ ] 每份规划文档是否把决策内容、仅供 agent 执行的细节和审计证据放在各自合适的层？
- [ ] 每个可删项是否都检查过：用户决策是否需要、是否可用更清楚的表格/图/不变量表达、agent 细节是否应进入 `implement.md`、审计证据是否应进入 `{TASK_DIR}/research/`，以及删除是否影响决策/执行/验收？
- [ ] 是否保留了用户明确请求、安全边界、兼容性要求、验收标准和完成验证必需的证据？
- [ ] 对 `reviewable` PRD，是否标记批准界面且不保留已解决问题？
- [ ] 需求覆盖、验收检查和实现检查是否仍然完整？文档更短本身不等于成功。

### 范围纪律

- [ ] 是否整理了 Task 并不要求的代码？
- [ ] 是否为尚不存在的场景新增了抽象、配置或扩展点？
- [ ] 是否为不可能发生的状态增加了推测性的回退机制？
- [ ] 是否修改了验收标准未提及的文件？
- [ ] 是否在调用方加入变通方案，而非在行为实际所在处修复？

## Step 5：跨层维度（如适用）

如果变更仅限单层，则跳过此步骤。

### A. 数据流（变更触及 3+ 层）

- [ ] 读取流是否正确：存储 → 服务 → API → 界面
- [ ] 写入流是否正确：界面 → API → 服务 → 存储
- [ ] 类型/模式是否在层间正确传递？
- [ ] 错误是否正确传播给调用方？

### B. 代码复用（修改常量、创建工具函数）

- [ ] 创建新内容前是否搜索了现有类似代码？
  ```bash
  grep -r "pattern" src/
  ```
- [ ] 如果同一值重复出现，它是否代表调用方必须一起改变的稳定概念？只有此时才提取——只是今天恰好相同的两个字面量应保持独立。
- [ ] 批量修改后，所有位置是否都已更新？

### C. 导入/依赖（创建新文件）

- [ ] 导入路径是否正确（相对路径与绝对路径）？
- [ ] 是否没有循环依赖？

### D. 同层一致性

- [ ] 使用同一概念的其他位置是否保持一致？

---

## Step 6：报告并修复

报告每项发现的违规，然后：

- 机械且局部的问题（lint 小问题、缺失类型、错误导入、死分支、失败断言）→ 直接修复，然后重新运行项目检查。
- 设计或判断问题（命名共享概念、移动模块边界、更改公开接口、重新分配行为所在位置）→ 记录证据和建议，然后停止。不得静默改写。

若修复会触及当前 Task 范围之外的文件，应说明并停止，不要自行扩大范围。
